## Exact proposed SQL and compatibility strategy

CLI-generated migrations (Supabase CLI 2.81.3; local file generation only):

1. `backend/supabase/migrations/20261113215813_harden_profiles_browser_privileges.sql`: atomic transaction, bounded lock/statement timeouts; if profiles exists, exactly `REVOKE TRUNCATE, TRIGGER ON TABLE public.profiles FROM PUBLIC, anon, authenticated;`. Postconditions check effective capabilities and membership-reachable roles, including NOINHERIT/SET ROLE and ownership paths. A remaining capability aborts/rolls back the whole migration. It **does not** revoke shared group grants, role memberships or ownership automatically. Owner must privately inspect provenance and design the narrowly scoped additional remediation when it aborts. This independent proposal can be reviewed without approving any signup-function replacement. Missing table is a fresh-install no-op; the baseline then secures it.
2. `backend/supabase/migrations/20261113215817_baseline_profiles_with_reviewed_adoption.sql`: creates a fresh profiles table only if missing. Existing tables must already match uuid/text/timestamptz types, id PK and validated auth.users.id FK; incompatible types/keys abort instead of coercion, replacement or backfill. Actual live types/nullability/extra required columns/defaults must be compared before adoption; supplied column names alone cannot prove compatibility. Existing data and extra columns are retained. Existing FK delete behavior is retained; fresh installation uses ON DELETE CASCADE.

The baseline grants authenticated SELECT/INSERT/UPDATE and service-role DML, revokes PUBLIC/anon table grants and authenticated DELETE/TRUNCATE/TRIGGER/REFERENCES. It enables RLS and adds separate permissive owner policies plus restrictive SELECT/INSERT/UPDATE guards (both USING and WITH CHECK for UPDATE). Existing policies remain, except six reserved `atoz_profiles_*` names are replaced by their repository definitions. Restrictive guards prevent an old broad authenticated permissive policy from bypassing ownership; existing restrictive policies may still deny legitimate access and need review. Browser BYPASSRLS/superuser/ownership/group capabilities cause a fail-closed postcondition. Table-level revocation does not remove separately granted column ACLs: inspect those privately, especially anon/PUBLIC; no broad role/schema grant changes are guessed here.

Fresh provisioning uses **new** `private.atoz_provision_profile`, SECURITY DEFINER, empty search path, schema-qualified objects/builtins, no browser/public/service function EXECUTE grants, AFTER INSERT ROW trigger. It is owned by the trusted migration role; review that role is private and cannot be assumed by browsers. Metadata only supplies optional display strings, never role/authorization fields. ON CONFLICT(id) DO NOTHING preserves existing profile values. No existing users are backfilled. A new function/trigger is installed only if no competing Auth triggers or function collision exists; ambiguous cases abort. Auth-trigger failures can block signup, so integration staging/isolated review is mandatory before live approval.

**Existing signup trigger is never replaced.** Baseline adoption requires an operator review fingerprint of its exact current definition. In the *same private migration session*, after security approval, set `atoz.reviewed_profiles_trigger_md5` to the reviewed `md5(pg_get_functiondef(trigger_function_oid))`; then apply the baseline. This is a deliberate review acknowledgement/drift gate, not cryptographic authorization. Do not automatically compute/set it in production scripts to bypass review. A hash/body change requires a new review. Reapplying the migration requires the same acknowledgement. Existing trigger must be enabled AFTER INSERT ROW. Its body, owner, ACL and search path remain unchanged: adoption does not claim that public.handle_new_user is hardened. Changes to that exact body/path require a separately reviewed migration after inspection; do not blindly ALTER search_path or CREATE OR REPLACE unknown code. The proposal is not approved for unattended db push/deployment; no workflow applies it live.

## Rollback and production gate

Transactions roll back on errors; local tests verify no partial hardening/policy adoption after failure. Once an authorized hardening transaction commits, **do not restore dangerous browser TRUNCATE/TRIGGER grants as rollback**. Preserve minimal DML and investigate client regressions. Keep the approved private pre-change ACL/owner/policy/function fingerprints and backups; no credentials/full function bodies in GitHub artifacts. Baseline never drops profile data or replaces the existing signup function. Fresh-install trigger removal/policy restoration, if later required, must be a separately reviewed forward fix from privately captured definitions; never DROP profiles or cascade Auth objects. App-image rollback does not undo database changes.

Production stays **NO-GO** until live privilege remediation is separately authorized/applied/reverified, exact provisioning code is security-reviewed, baseline adoption compatibility is approved, and existing Docker/systemd, recovery access, backups/restore and release-image gates pass. This change establishes repository-level remediation readiness only; production was untouched.
