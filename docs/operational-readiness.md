## Configuration and runtime audit

Frontend: `VITE_SUPABASE_URL=https://<approved-project>.supabase.co`, `VITE_SUPABASE_ANON_KEY=<public-anon-placeholder>`, `VITE_API_BASE_URL=/api`. These are immutable build inputs. The public-key guard rejects privileged credential types; it does not validate actual credentials. Backend: `SUPABASE_URL=https://<same-approved-project>.supabase.co`, `SUPABASE_ANON_KEY=<public-anon-placeholder>`, `SUPABASE_SERVICE_ROLE_KEY=<private-backend-only-placeholder>`. Never use synthetic CI images as production frontend images. No real values belong in this document.

The staging guard now checks *every* configured frontend/backend URL, including empty or contradictory backend values, rather than accepting the first URL. It remains a staging-only guard, not production authorization. Public and backend project equality must be checked in the approved production build manifest without disclosing keys.

Docker keeps backend/frontend non-root, read-only roots, dropped capabilities, resource limits and no-new-privileges. Repository Compose logs are now bounded to 3 × 10 MB per container; external retention/alerting remains an owner prerequisite. Frontend local health bypasses inherited HTTP proxies. Backend health requires the expected JSON status, but is **liveness only**, not Auth/database readiness. Caddy waits for healthy frontend; backend is in a separate Compose project and must be explicitly gated first. External `atoz_net` must exist. Caddy data/config volumes preserve certificates across rollback. Backend port exposure and Docker/systemd overlap must be inventoried before any change. Do not stop either backend merely because both exist.
